04 — Knowledge System

How Knowledge is Stored and Used

Knowledge is stored in a tiered markdown memory system at memory/. Tiers are loaded selectively — only what the current task needs. This keeps each session lean while preserving full project context across sessions.

Tier 1 — Session Bootstrap

Load Every Session

  • context/project_state.md — active phases, open items, next actions
  • context/domain_rules.md — terminology, tone, invariant rules
  • reference_confluence.md — Confluence page IDs, Miro, SharePoint
Tier 2 — Phase Knowledge

Load for Phase Work

  • phase1/state.md — 5 letter types, routing, field specs, D-01..D-17
  • phase2/state.md — batch XLS flow, 4 types, acceptance design
  • phase3/state.md — ex-employee access, auto-trigger, delivery model
Tier 3 — Source Knowledge

Load When Needed

  • img_*.md — extracted field specs per screenshot
  • kb_*.md — platform technical limits, deep context notes
  • Loaded only for the specific letter type or topic being worked on
Tier 4 — Archive

Do Not Load

  • Superseded knowledge files
  • Hook artifact stubs
  • Original files absorbed into phase state files

Feedback & Decisions Log — Single Source of Truth

All confirmed design decisions (D-XX), open questions (OQ-XX), and stakeholder feedback (F-XX) are recorded in output/shared/Feedback_Decisions_Log.md. Every output document must be consistent with the locked decisions. The validation skill reads this file first on every run and derives all facts dynamically — nothing is hardcoded in the validator.
