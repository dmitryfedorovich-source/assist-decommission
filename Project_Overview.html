01 — Context

Why This Project Exists

assist.epam.com is being decommissioned. India employees currently use Assist to request official HR letters. Every workflow must move to docs.epam.com by June 30, 2026.

📋

The Problem

India HR document workflows live exclusively in Assist — a platform being retired. Employees need uninterrupted access to reference letters, compensation letters, and separation documents.

🎯

The Goal

Migrate all India HR letter workflows to EPAM Docs with no degradation in employee experience. Replicate existing processes, remove legacy dependencies, and go live by June 30, 2026.

🤖

The Approach

An AI-assisted BA documentation workflow — Claude Code processes inputs, maintains a persistent knowledge base, generates multi-audience docs, and validates consistency automatically.

Deadline: June 30, 2026 — Assist Reference Letters retired. All India employees must be onboarded to EPAM Docs before that date. Phase 1 (Reference Letters) is the critical path item.

02 — How It Works

AI-Assisted Documentation Workflow

Raw inputs are processed through a structured knowledge pipeline. Extracted facts are stored in a tiered memory system. Claude Code uses that memory to generate, update, and validate all output documents.

Raw Materials
Screenshots · Transcripts · Confluence · Corrections
→
Knowledge Extraction
Claude Code reads & extracts decisions, facts, field specs
→
Memory System
Tiered markdown files persist knowledge across sessions
→
Document Generation
Claude writes / updates output docs per audience rules
→
Validation
validate-docs skill checks all 21 docs for consistency
→
Delivery
Stakeholder review · sign-off · dev handoff

Key principle: The Feedback & Decisions Log is the single source of truth. Every output document is derived from locked decisions in the log. When a decision changes, the validator catches which docs need updating. The AI never invents facts — it extracts, stores, and applies them.

03 — Inputs

What Feeds the System

Six input types are supported. Each is processed differently and results in structured knowledge stored in the memory system.

📸

Screenshots — Assist Platform

JPEG/PNG screenshots of Assist forms, flows, and UI. A pre-read hook intercepts every image access: if a memory file already exists for that screenshot, the hook redirects to the cached file instead of re-reading the image — saving processing time.

  • Form field names and types
  • Dropdown option values
  • Workflow step sequences
  • UX behaviors (popups, warnings)
🌐

Live Confluence Pages — MCP

Direct integration with kb.epam.com via the Confluence MCP server. Pages are read in real time — no stale exports. The EPMEOADOCS space contains 7 tracked pages covering all letter types, process flows, open questions, and communication history.

  • Confirmed process decisions per letter type
  • Open questions log (India Team confirmations)
  • Communication history (7 meetings)
  • Dev trackers for each phase
🎙️

Meeting Transcripts

Auto-transcribed meeting recordings dropped into input/transcriptions/. Each transcript is processed: decisions and facts are extracted, the Feedback Log is updated, relevant phase state files are updated, and the file is renamed with a [processed]- prefix.

  • Stakeholder confirmations and rejections
  • Design decisions with owner and date
  • Open questions raised
  • Action items and next steps
✏️

Stakeholder Corrections

Handwritten correction images from document review sessions. Claude reads the image, identifies what was marked as wrong, applies the correction to the relevant output documents, and logs a Feedback entry (F-XX) in the Decisions Log.

  • Date corrections (e.g. July 1 → June 30)
  • Process step corrections
  • Terminology fixes
  • Approval flow updates
📝

Meeting Notes

Pre-meeting briefs and background notes from the BA team stored in input/meeting_notes/. Provide context for upcoming stakeholder sessions and help frame questions for India SME meetings.

📁

Confluence HTML Exports (Legacy)

Static HTML exports from early project phases, now archived. The live MCP integration replaced these as the primary source for Confluence content — exports are retained for historical reference only.

04 — Knowledge System

How Knowledge is Stored and Used

Knowledge is stored in a tiered markdown memory system at memory/. Tiers are loaded selectively — only what the current task needs. This keeps each session lean while preserving full project context across sessions.

Tier 1 — Session Bootstrap

Load Every Session

  • context/project_state.md — active phases, open items, next actions
  • context/domain_rules.md — terminology, tone, invariant rules
  • reference_confluence.md — Confluence page IDs, Miro, SharePoint
Tier 2 — Phase Knowledge

Load for Phase Work

  • phase1/state.md — 5 letter types, routing, field specs, D-01..D-17
  • phase2/state.md — batch XLS flow, 4 types, acceptance design
  • phase3/state.md — ex-employee access, auto-trigger, delivery model
Tier 3 — Source Knowledge

Load When Needed

  • img_*.md — extracted field specs per screenshot
  • kb_*.md — platform technical limits, deep context notes
  • Loaded only for the specific letter type or topic being worked on
Tier 4 — Archive

Do Not Load

  • Superseded knowledge files
  • Hook artifact stubs
  • Original files absorbed into phase state files

Feedback & Decisions Log — Single Source of Truth

All confirmed design decisions (D-XX), open questions (OQ-XX), and stakeholder feedback (F-XX) are recorded in output/shared/Feedback_Decisions_Log.md. Every output document must be consistent with the locked decisions. The validation skill reads this file first on every run and derives all facts dynamically — nothing is hardcoded in the validator.

06 — Capabilities

What the System Can Do

The workflow combines Claude Code's AI capabilities with a structured project framework, enabling a range of BA documentation tasks that would otherwise require significant manual effort.

📸

Image & Screenshot Analysis

Reads Assist platform screenshots and extracts field names, types, dropdown options, flow sequences, and UX behaviors. Results are cached in memory files and re-used in future sessions without re-reading the image.

🌐

Live Confluence Integration

Reads and searches Confluence pages in real time via MCP. Can fetch any page by ID, search within a space, and retrieve child pages. No stale exports — always reads current content from kb.epam.com.

🎙️

Meeting Transcript Processing

Extracts decisions, open questions, and action items from raw meeting transcripts. Updates the Feedback Log, phase state files, and project state automatically. Marks processed files with a prefix to prevent reprocessing.

✏️

Stakeholder Correction Application

Reads handwritten correction images, identifies what changed, applies corrections to all affected output documents simultaneously, and logs the change as a Feedback entry with source and date.

📝

Multi-Audience Document Generation

Generates different documents from the same underlying facts, with tone and content adapted per audience — management language for onepagers, structured questions for SME validation, plain instructions for employee guides.

🔍

Cross-Document Consistency Validation

Runs the validate-docs skill across all 21 output documents simultaneously, checking factual accuracy, terminology, audience fit, structural completeness, OQ cross-references, and forbidden phrases. Errors and warnings are reported with file, location, and fix.

💾

Persistent Cross-Session Memory

Stores project knowledge in structured markdown files that survive across sessions. Starting a new session loads only what's needed (tiered approach). The system "remembers" all prior decisions, open questions, and confirmed facts without re-reading source material.

📊

Decision & OQ Tracking

Maintains a living Feedback & Decisions Log with full traceability — every decision has an owner, date, source, and list of documents it is reflected in. Open questions have owners and target resolution stages. Nothing slips through.

07 — Automated Validation

The validate-docs Skill

Running /validate-docs triggers a full consistency check across all output documents. The skill reads the Feedback & Decisions Log first, derives all facts dynamically, then runs all checks. No hardcoded values — the validator always reflects the latest locked decisions.

⚡
/validate-docs
Run after any change to output/ — validates all output documents in one pass
Check 1 — Factual accuracy vs. locked decisions ("Reflected in" verification)
Check 2 — Forbidden phrases (RM approval, July 1, HRBP in wrong docs, etc.)
Check 3 — OQ cross-reference integrity (cited OQs exist; resolved OQs not open)
Check 4 — Terminology consistency (letter names, platform name, role names)
Check 5 — Structural completeness per document type
Check 6 — Audience fit (management / SME / employee language rules)
Check 7 — Internal coherence (no contradictions, no orphaned placeholders)
Check 8 — Traceability completeness (RTM rows, Source Index, OQ Impact Map)
Check 9 — Confidence quality (uncertainty markers in management docs, SME question coverage)
Check 10 — Stale detection (superseded decisions, stale memory files, orphaned pending markers)

❌ Errors

Must fix before next stakeholder meeting. Reported with file, location, issue, correct content, and source Decision ID.

⚠️ Warnings

Review recommended. Reported with file, location, concern, and specific suggested action.

✅ Pass

Confirms documentation is consistent with the Feedback Log and ready for the next stakeholder stage.

10 — PO/BA Playbook

How to Use This System

A practical guide for the BA or PO running this project — when to feed information, how to create and update each output document, and when to validate.

📥

1 · Feed Inputs

When new information arrives — meeting transcripts, stakeholder corrections, Confluence pages, verbal decisions — drop it into the system. Claude extracts decisions and open questions, updates the Feedback Log, and flags what output docs need to change.

✍️

2 · Generate & Update Artifacts

With confirmed facts in memory, ask Claude to create or update the relevant output document. Load the phase state file and domain_rules first. The Feedback Log is the single source of truth — Claude never invents facts. Run /validate-docs after every change.

✅

3 · Verify & Sign Off

Run /validate-docs before every stakeholder stage. Fix all errors before sharing documents. Review warnings and accept or resolve each one. The validator reads the Feedback Log dynamically — no setup required.

Common Step-by-Step Workflows

🎙️ Process a Meeting Transcript

  1. Drop transcript file in input/transcriptions/
  2. Tell Claude: "Process the new transcript"
  3. Claude extracts D-XX / OQ-XX / F-XX → updates FDL → updates phase state → renames file with [processed]- prefix
  4. Run /validate-docs — check what output docs need updating
  5. Apply required fixes; re-run /validate-docs until clean

✏️ Apply Stakeholder Corrections

  1. Save correction image in input/corrections/
  2. Tell Claude: "Apply corrections from [filename]"
  3. Claude reads image → identifies changes → updates all affected output docs → logs F-XX in FDL
  4. Run /validate-docs to confirm corrections propagated cleanly across all docs

🔒 Add a Confirmed Decision

  1. Add D-XX entry to output/shared/Feedback_Decisions_Log.md (follow templates.md)
  2. Add matching row to output/shared/RTM.md
  3. Add entry to docs/data/decisions.yaml
  4. Run /validate-schema to confirm sync across all three files
  5. Run /validate-docs → update all flagged docs → re-run until clean

📋 Prepare for an India SME Meeting

  1. Run /validate-docs — resolve all errors first
  2. Review Open OQs in FDL with "Stage 2 review" as target resolution
  3. Confirm each open OQ has a corresponding question in 05_India_SME_Validation.md
  4. Check sign-off table in 05 has India stakeholder names
  5. Share 05 with Satish / Satya / Sasanka for review; record responses as new D-XX or OQ updates

Validation rule: Run /validate-docs after every change to any file in output/. This is the single quality gate for the entire documentation set. All ❌ errors must be fixed before sharing any document with a stakeholder. ⚠️ warnings must be reviewed and either resolved or explicitly accepted with a note in the FDL. Run /build-overview after any change to docs/src/ — never edit Project_Overview.html directly.
